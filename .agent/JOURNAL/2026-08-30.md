# 2026-08-30

## What this pass built

The working system itself: `.agent/`, a standing prompt with no dated fact in
it, a state file nobody writes by hand, a queue, and this journal. No file under
`src/` changed.

## Why

A handoff written on 2026-08-27 opened a session on 2026-08-29 with four claims
about the repository. All four were wrong: it said the tree was clean (thirteen
modified files), that HEAD was on `196b441` (five commits further on), that the
version was 2.8.0 (2.8.1), and that the offline gates ran in series and
parallelising them was the first untouched opportunity (`run-gates.mjs` had been
pooling one worker per core, with a `--jobs` flag, all along).

The lesson is not that the author was careless. It is that prose about a
repository decays at the speed the repository moves, and that a frame and a
state cannot live in the same file. So `PROMPT.md` is forbidden from containing
a version, a commit, a count or a current open point, and `ETAT.json` is
forbidden from being edited.

## What the generator found on its first run

Three things nobody had asked it for, which is the argument for having it.

**A third remote.** `public` and `origin` point at the same URL. `public`'s
tracking ref is stale, so it reported 16 commits ahead for a repository `origin`
reported up to date. Every look at the remotes this week had used
`git remote -v | head -2` or `head -4`, which cut before the third line: the
"there is no origin" claim made earlier that day came from the truncation, not
from the repository. `state.mjs` now names remotes that share a URL.

**Nineteen orphan harnesses of thirty-three.** The runner enumerates eighteen
gates. Everything written since is on disk and in no runner, including the three
live harnesses that are the only coverage of the language UI reworked this week.

**Two bugs in the generator, caught by reading its own output.** It reported
thirty-six gates because the regex matched every quoted string in the block,
counting each gate's script path as a gate. And it printed `undefined ouvert(s)`
because `PLAN.md` did not exist yet and the absent case returned no counters.
Both fixed before the file was used for anything.

## The gate suite had been red for a day, and nobody had looked

Running `run-gates.mjs` for the first time this week returned exit 1 on two of
its eighteen gates. Both had been failing since `62b669e`, committed the day
before.

**`audit-rtl`** flagged `right: auto` in `.kt-lang-panel-fixed`. The audit
already carried that exact exception for `.kt-chip-menu-fixed`, with the reason
written next to it: the placement function writes viewport coordinates, which
are physical by definition, and the logical property above must not fight them.
The panel arrived later with the identical construct and was never added. Stale
allowlist, not a defect. Fixed, and checked both ways: with the exception the
audit exits 0, without it exits 1.

**`chip-live`** failed six assertions across three renders, all of the form "a
click on the code opens the list instead of toggling". That is the change made
on request the same day. The gate encoded the old contract, exactly as three
unit tests did, and those were retargeted while this one was not, because the
unit tests run in `npm test` and this does not. Retargeted the same way: a click
opens wherever it lands, the next click closes. Both assertions kept and turned
around, since keeping only one would pass a chip that opens and never closes.

**`audit-da`** then surfaced three findings, all on the drawn flags: an inset
hairline in each theme and a 2px radius. The direction bans the drop shadow;
`inset` is a line painted inside the box, and without it Japan's flag is an
invisible white rectangle on `#171A1C`. A 4px radius on a box 12px tall eats a
third of its height. The audit had no way to express an exception, so one was
added, narrow: that selector, those two properties. Checked against six cases,
six correct, including that a shadow on `.kt-compose` and a radius on
`.kt-chip-menu` are still caught, and that duration on `.kt-flag` still is.

Result: 18/18 green, 19.2s of wall clock against 106s of cumulative work, six
workers, a factor of 5.52.

**What this says about today.** "Gates green" was said several times over this
session meaning typecheck, lint, test and build. The eighteen-gate suite was
never run once, and two of its gates were red the whole time, one of them made
red by a change made that day. Four commands are not the gates; they are four of
them.

## The apparatus does not survive a machine

`git ls-files scratchpad/` returns 0. Every gate, every harness and every audit
is under a directory `.gitignore` excludes at line 18. They exist here and
nowhere else, and a fresh clone of the public repository gets none of them,
including the runner `PROMPT.md` instructs the next session to run.

State that survives a session limit is worth little if the means of checking it
does not survive a machine. It is the first open item in `PLAN.md`, priced
rather than fixed: moving it in publishes every measurement script and the
screenshots they write, which is a decision about what the public repository is
for, and that decision is kil's.

## Second pass: the apparatus now survives a machine

Taking the first open item, which was the one that undermined the rest.

**What made it hard, measured before deciding.** Playwright is not a dependency
of this project, and 33 harnesses each carried the same absolute path into one
home directory as its fallback location. There is CI, two jobs on node 20, and
it never runs these gates: adding Playwright as a devDependency would pull
browser binaries into both installs for nothing. And the split that settled what
to track: 422 KB of scripts against 272 MB of screenshots, HTML dumps, bundles
and browser profiles.

**What was done.** A single `scratchpad/harness/playwright.mjs` resolves the
browser from `$UX_KIT`, then from a gitignored `scratchpad/uxkit.path`, then
from the repository's own `node_modules`, and exits 2 when none of the three is
there, printing all three ways to fix it. Exit 2 and not 1, because a machine
without Playwright is a missing prerequisite and not a failed gate, and a runner
that cannot tell those apart reports the first as a product defect. The 33
harnesses import it. `.gitignore` re-includes `*.mjs` and `audit_*.py` under
`scratchpad/` and nothing else, so 40 files and 291 KB enter and every output
stays out, along with the French working prompts.

**Three things went wrong doing it, all mine.** The bulk rewrite missed
`snapshot.mjs`, whose two lines were written on one line. It missed
`measure-popup.mjs`, which had its own home-made resolver, and then turned
`const chromium = await loadChromium();` into `const chromium = chromium;`,
which the gate caught as "Identifier 'chromium' has already been declared". And
the first gate run after the rewrite failed with exit 2 everywhere, correctly:
the private path was gone and nothing had replaced it yet, which is what the
`uxkit.path` file is for.

**Verification.** `node --check` on all 35 harnesses, then 18/18 gates green,
19.5s of wall clock against 114.2s cumulative, factor 5.86. Then typecheck,
lint, 620/620 tests and build. The gates are the verification of a mechanical
rewrite across 33 files; reading the diff would not have caught
`const chromium = chromium;` as fast as running it did.

**Left open on purpose.** 19 harnesses of 35 are still in no runner, and the
live ones still have no entry point. Tracking them was the prerequisite for
fixing that, not the fix.

## Third pass: a harness nobody ran was reporting a real bug

Taking the runner-coverage item. Classifying the orphans first, by measurement
rather than by name: 6 offline and 13 live, and of the 6 offline, 3 assert
nothing at all. Those three draw images and print numbers for a human;
wiring them would buy runtime and no verdict, so they stay out and the runner
now says so in place.

Of the three offline orphans that do assert, two passed and were wired.
`bar-panel-live` failed on three counts. Two were the old contract, the same
retargeting as the unit tests: it read the favourite tiles' visible text, which
was removed the day before, and it capped the panel at 45% of the chat when the
panel had deliberately grown to show 25 rows instead of 6. The third was
`the panel leaves the window`, and it was real.

**The bug it was pointing at.** Replacing that boolean with the four edges, as
this journal already argued for once today, gave `gauche: -4`. Then the live
harness at three window sizes: clean at 1500x950 and 1280x900, and at 1000x750
the panel sat at y=711 with `bas: -362.2`, a third of the list below the bottom
of the screen. Instrumenting the placement showed the inline style saying
`top: 222px` while the element rendered at 711, which is not a placement error
at all: a `position: fixed` element is only viewport-relative while no ancestor
establishes a containing block, and walking the ancestors named the culprit as
`div.kt-float`, carrying a `backdrop-filter`. The bar's own top is 489, and
489 + 222 = 711 to the pixel. Our CSS, not Kick's.

The fix is the one already used twice this week for the same family of problem:
hang the panel off the body. It also survives Kick adding a transform above the
bar, which no amount of care inside the bar would.

I speculated twice about why before instrumenting, and stopped on the second,
which is the rule. Reasoning about `left: 206px` rendering at -4 was never going
to converge; asking the DOM which ancestor stole the containing block took one
probe.
